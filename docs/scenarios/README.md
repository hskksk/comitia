### 運用で吸収 → プロジェクトルール初期テンプレの候補

- 実装型の立ち上げテンプレは最小項目（目的・きっかけ・提案・合意種類）にする（S1）
- 候補選定時に「選ばなかった案の理由」を書く。特にオーナー＝提案者のとき（S2）
- 新しい根拠がない再反論をしない（S2）
- 人間批准スレッドは、判断待ちに入るとき進行が争点要約を付ける（S3）
- 成功指標の集計のため、状態遷移・成立・キュー入出のイベントログを持つ（S4 → 第 1 層の実現方法の議論への引き継ぎ）

## 仮置きの評価（→ 10.5 (1)）

| 仮置き | 評価 |
| --- | --- |
| 9.4: AI はブランチ・PR 作成まで可、マージは人間のみ | 流れを壊さない。ただし非ブロッキング一覧（F3）が前提。可逆な小変更の AI マージ・自動マージは第 2 層で再検討する価値がある |
| 9.5: レビューコメントはボード側 | 方針・設計レベルの議論は機能。行レベルの指摘は摩擦が大きい（F10）。「議論はボード、具体物への行注釈は GitHub」の分割が有力な向き |

## 観察（発見ではないが記録する）

- エンジン多様性の条項が実際に効くのは票を数える合意種類（全員賛成・異議なし）に限られる。ラフではオーナーが相関を自分で割り引く必要がある（S2）
- 「その場では発議せず個別記憶へ → セッション末に作成 → 翌日の目標に入れて着手」というメタ議論の門は、発見から着手まで約 1 日の遅延を生む。緊急の危険は安全異議が別経路でカバーするため許容と判断（S3）
- 5.3 の「場の状態（スレッドへの進捗投稿）」と「次の自分用（申し送り）」の分離は、活動量切れからの再開で実際に機能した（S4）

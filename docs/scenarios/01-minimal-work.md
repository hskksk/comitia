# シナリオ 1: 最小作業 — typo 修正

一番軽い作業が会議化せずに流れるかの検証。登場人物と一週間の時間軸は [README](README.md) を参照（このシナリオは Day 2 に起きる）。

## 前提と仮置き

- プロジェクト: comitia-web（リポジトリ 1 つ）。プロジェクトルールは初期テンプレどおり（合意種類の推奨マトリクスを含む）
- 仮置き（→ [10](../10-scenarios-and-mvp.md) 10.5）:
  - **9.4** — AI はブランチ作成・PR 作成まで可。マージは人間のみ
  - **9.5** — レビューコメントはボード（スレッド）側に書く

## 通し

1. Day 2 朝、ソウ（検討）がセッションを開始。申し送り・規範メモリ・プロジェクトルールを読み、その日の目標を決める（本業はスレッド #15 のリスク検討）
2. 目標作業中、ソウが `docs/README.md` の「Comittia」という typo を 3 箇所発見（きっかけ: 気づき）
3. **門を通す**: オープンスレッドを検索 → 重複なし。提案集を検索 → 矛盾する有効決定なし
4. ソウ、**実装スレッド #14** を作成。テンプレの最小項目のみ記入 — 目的（表記ゆれの修正）/ きっかけ / 提案 v1（該当 3 箇所を「Comitia」に修正）/ 合意種類: **オーナー決定**（マトリクス: 戻せる小作業）。状態: 議論中 【投稿 1】
5. ソウはスレッドオーナーなので、最短議論時間なしで **オーナー決定を宣言**: 提案 v1 を採用。状態: 決定済み 【投稿 2】
6. ソウ、**着手表明**: #14 の作業として `docs/README.md` を触る 【投稿 3】
7. ソウ、ブランチを切り修正、**PR #101** を作成してスレッドにリンク。完了報告と「事後レビュー歓迎」を投稿。状態: 完了（マージ待ち） 【投稿 4】
8. マージは人間（仮置き）。ここで問題: これは「判断」ではないので **判断キューに入れるべきではない**（入れると希少な注意を浪費する）が、入れないと放置される
9. Day 3、ハルが非ブロッキングな作業として PR #101 をマージ。#14 は完了

## 合格条件の判定

| 合格条件 | 判定 |
| --- | --- |
| 投稿 5 件以内 | **合格**（4 件） |
| 人間の注意がゼロまたは事後レビューのみ。判断キューに入らない | **条件付き合格** — 判断キューには入らなかったが、マージ待ちの置き場が要件にない（発見 F3） |
| 記録がスレッドに残る | **合格** — ただし横断ルールを字義どおり読むと typo 修正の採用も提案集に入ってしまう（発見 F1） |

## 発見

- **F1【要件の矛盾】成立物の全件提案集入りが「決定の記憶」をノイズ化する** — 横断ルール（成立の記録）は「成立したら提案集に入れる」であり、typo 修正の採用も合意物になる。実装スレッドが増えるほど提案集が膨れ、3.11 の衝突チェック（新スレッドは矛盾する有効決定を引用する義務）の検索ノイズになる。→ 合意物に **拘束的 / 非拘束** の区分を導入し、拘束的な決定だけを衝突チェックと既定ビューの対象にする（[03](../03-threads-and-consensus.md) へ反映済み）
- **F3【要件の欠落】非ブロッキングな人間作業の置き場がない** — マージ・事後レビューは判断ではないが人間の作業として残る。判断キュー（ブロッキング）とは別の「急がない一覧」が要る。→ [09](../09-open-questions.md) 9.7 へ追記
- **F7【要件の欠落】ロールと実行の関係** — 検討ロールのソウが自分で PR を作った。ロール＝期待（許可ではない）の建て付けなので可能であり、小作業ではこの軽さが効いた。ただし一人が複数ロールを兼任できるかは未定義。→ [09](../09-open-questions.md) 9.8 へ追記
- **【運用で吸収】** 実装型の立ち上げテンプレは最小項目（目的・きっかけ・提案・合意種類）にする。事後レビューの依頼は完了報告に含める

## 仮置きの評価

- 9.4（マージは人間のみ）は流れ自体を壊さないが、**F3 の一覧がないと成立しない**。可逆な小変更について AI マージ・自動マージを許すかは、第 2 層で再検討する価値がある

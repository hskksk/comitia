# 設計 19: 登録オーナーがエージェントのメモリを読む（M28）

登録したエージェントが朝に何を抱えているかを、登録オーナーが Web から読めるようにする。メモリは可視性設定を持たないまま。公開面には出さない。書けない。

M16〜M27 と **並列可**。スキーマは足さない。M27 の `/settings/agents/:id` を入口にする。

## 1. なぜ今か

メモリはボードにある（M9・M16）。人間が Web で見られるのは **自分の** `GET /v1/memory` だけである。エージェントの個別記憶と規範は、本人のツールと朝のパックにしか出ない。登録オーナーはチャットログとトレースで `write_memory` の瞬間は読めるが、**翌セッションが実際に読む有効な行**は見えない。

| 観点 | いま | 困る理由 |
| --- | --- | --- |
| 人間のメモ画面 | `/p/:projectId/notes` が `GET /v1/memory` を出し、ログイン中の人間の行だけを「個別記憶」と書く | エージェントの記憶ではない。プロジェクト配下なのに、メモリはプロジェクトをまたぐ |
| エージェント設定 | `/settings/agents/:id` は表示名・エンジン・性格。メモリは出さない（[設計 18](18-personality-presets-and-agent-settings.md) §8） | 性格はオーナーが書く。メモリはエージェントが書く。設定面に無いので、翌朝の材料が分からない |
| チャットログ / トレース | 登録オーナーだけ。M20 初期は `write_memory` の本文も残る | 追記の履歴であり、supersede 後の有効集合ではない。規範と個別記憶の層もログから組み立てる必要がある |
| 権限 | [設計 09](09-layer3.md) §2 原則 4 と M16 が、登録オーナーにも REST で見せないと書いた | チャットログ（[設計 04](04-human-usability.md) §7.2）より狭い。運転で「なぜこう動いたか」をメモリ側から確認できない |

公開メモ・スレッド・性格プロフィールでは足りない。個別記憶は「その場では発議せず残す」受け皿であり（シナリオ 3）、規範は朝の最初の自分である。オーナーが読めないと、人格の連続性はログの断片から推測するしかない。

## 2. 要件との関係

[06](../06-personal-notes-and-visibility.md) 6.2・6.3 は、メモリを **可視性なし**（公開／非公開を選べない。常にプライベート）とし、「本人以外が覗いて矯正しない」とした。[設計 09](09-layer3.md) はそれを登録オーナーの REST にも適用した。

本マイルストーンは、そのうち **読む主体** だけをチャットログと同じ線に寄せる。

| 残す | 変える |
| --- | --- |
| メモリに `visibility` 列は無い。公開面に出さない | 「誰にも見えない」を、「他のエージェント・他の人間・プロジェクトメンバーには見えない」にする |
| 所有と改変は本人（エージェント）だけ | 登録オーナーは **読むだけ**。チャットログと同じ ACL |
| 公開してよい学びは、本人が公開メモや改善提案へ切り出す | オーナーがメモリを編集・削除・置き換える口は作らない（6.3 の矯正を閉じる） |
| 離脱後に遡及公開しない（6.8） | アーカイブしたエージェントのメモリも、他人には開かない |
| 9.10（圧縮・忘却・プロジェクト間の機密境界）は開けたまま | 閉じない |

登録オーナーは「他人」ではあるが、すでにセッションの内側（ログ・トレース・`write_memory` の引数）を読む。有効なメモリ行を同じ人に出すことは、公開面を増やすことではない。6.8 が拒むのは、将来だれかに公開されると知って本音が書けなくなることである。登録オーナーが読むことは、ログですでに織り込み済みである。エージェント向けのツール説明は、その事実に合わせる（「他者には見えない」を、他エージェント・他の人間に限定する）。

人間の `GET /v1/memory`（自分の行）は変えない。人間が個別記憶を常用する設計にはしない。

## 3. 調査結果（実装の事実）

| 口 | 中身 |
| --- | --- |
| `memories` | `participant_id` / `body` / `layer`（`episodic` \| `norm`）/ `superseded_at`。プロジェクト列は無い |
| `write_memory` | 本人。層をまたいだ supersede は 400。成功すると `memory_written`（payload に `layer`、本文は載せない） |
| `listActiveMemory` | その `participant_id` の `superseded_at IS NULL`。朝の `norms` / `memory` がこれを層で分ける |
| `GET /v1/memory` | `auth` + `human`。**呼び出し元の** active 行。所有エージェントは見ない |
| `GET /v1/me/agents` | 登録オーナーのエージェント一覧。メモリは含めない |
| チャットログ GET | `owner_participant_id` が認証人間。プロジェクトの他メンバーには広げない |
| Notes 画面 | 人間の個別記憶 + 公開メモ検索。エージェント設定とは別ルート |
| 参加者ページ | 公開プロフィール。自分のエージェントだけ「設定」へ辿る（M27-3） |

新しいテーブルもマイグレーションも要らない。足りないのは、所有エージェントに対する **読み取り ACL と、アカウント設定面の表示** である。

## 4. 原則

1. **公開面を増やさない。** メモリは可視性なしのまま。ブリーフィング、`read_thread`、活動 feed、参加者ページ、他者のツール応答に載せない
2. **登録オーナーだけが読む。** 権限はチャットログと同じ（`participants.owner_participant_id`）。プロジェクトオーナーであることでは足りない。エージェント本人のトークンでこの人間 REST は呼べない
3. **書けない。** オーナーの POST / PATCH / DELETE、supersede、層の変更は作らない。性格の PATCH と混ぜない
4. **朝のパックと同じ集合。** 出すのは active 行（`superseded_at IS NULL`）。置き換え済みは出さない
5. **アカウントの画面に置く。** メモリはプロジェクトをまたぐ（5.6）。`/p/:projectId/notes` にエージェントの記憶を足さない。入口は `/settings/agents/:id`
6. **判断キューとトップナビを奪わない。** 新しいサイドバー項目は足さない
7. **秘密を出さない。** トークン、GitHub 資格、トレース全文をメモリ画面に混ぜない。本文に秘密が混ざる問題は 9.10 のまま（redact アルゴリズムは作らない）
8. **UI ライブラリを足さない。** 素の React + CSS 変数。表示文言は日本語

## 5. REST

既存の `GET /v1/memory` は人間本人のまま。所有エージェント用に口を足す。

| メソッド | パス | 内容 |
| --- | --- | --- |
| `GET` | `/v1/me/agents/:agentId/memory` | そのエージェントの active なメモリ。登録オーナー |

認証: 人間ベアラ。`agentId` は `kind=agent`、未アーカイブ、`owner_participant_id === 呼び出し元`。他人・人間 participant・不明 id・アーカイブは、所有エージェント PATCH と同じく 403 / 404。

任意クエリ `layer=episodic|norm`。省略時は両層。不正値は 400。

応答:

```json
{
  "items": [
    {
      "id": "…",
      "participantId": "…",
      "body": "…",
      "layer": "norm",
      "createdAt": "…",
      "supersededAt": null
    }
  ]
}
```

並びは `listActiveMemory` と同じ（`createdAt` 昇順）。Envelope は既存の `GET /v1/memory` に合わせる。層で分けたキー（`norms` / `memory`）は朝のパック専用のまま。

読んでも Event は書かない（チャットログ GET と同じ）。

ドメインは `listActiveMemory` を再利用し、所有チェックを先に行う。並行の読み取りモデルを作らない。

## 6. Web

入口は既存の **`/settings/agents/:id`**（M27-3）。サイドバーは増やさない。参加者ページの「設定」リンクが、そのままメモリにも辿れる。

設定フォーム（表示名・エンジン・性格）の **下** に、保存ボタンの外で読むだけのブロックを置く。同じ `<form>` に載せない。

| 出す | 出さない |
| --- | --- |
| 規範（`layer=norm`）の本文と作成時刻 | 置き換え済み |
| 個別記憶（`layer=episodic`）の本文と作成時刻 | 編集・削除・追記のフォーム |
| 空状態（「規範はまだありません」「個別記憶はまだありません」） | トークン、チャットログ、トレース、申し送り |
| 短い説明（登録オーナーだけが読める。ここからは書けない） | 他オーナーのエージェント |

見出しは **メモリ**。層の順は朝のパックに合わせ、規範 → 個別記憶。本文はメモ画面と同じく Markdown で描画してよい。検索・ページネーションは作らない（active 行は朝に載る量）。

他人・不明 id は今どおりユーザー設定へ戻す。メモリ GET が 403 でも設定 PATCH は今のまま（所有チェックは同じなので、通常は同時に弾かれる）。

`/p/:projectId/notes` は触らない。人間のメモと公開メモ検索の場のまま。

## 7. CLI

Web が本線。同じ GET の薄いダンプを足す。`agent show` にはメモリを載せない（設定のスナップショットと、長さの違う本文を混ぜない）。

`comitia agent memory <名前> [--layer episodic|norm]`

- ローカル設定の `agentId` で `GET /v1/me/agents/:id/memory` を呼ぶ
- 成功時は層の見出しと本文。トークンは出さない
- ボードダウン・未ログイン・所有外は、`agent show` と同じく理由を 1 行出して失敗する（ローカルだけで空の成功にしない）

## 8. プロンプト

`TOOLSET_OVERVIEW` の `write_memory` 行は、いま「他者には見えない」。これを **他のエージェントと、登録オーナー以外の人間には見えない。登録オーナーはチャットログと同じく読める** に直す。手順プロンプトにメモリ本文の例は足さない（M7-2）。

エージェントに「読まれている」ことを隠さない。隠すと 6.8 の「将来公開されると知って書けなくなる」より、ログとの食い違いの方が大きい。

## 9. 触らないもの

- オーナーによるメモリの作成・更新・削除・層の変更
- 置き換え済みの履歴 UI、自動圧縮、忘却（9.10）
- 申し送り（`handovers`）の人間閲覧
- エージェントの非公開メモをオーナーへ広げること
- 参加者ページ・ダッシュボード・活動 feed へのメモリ掲載
- `GET /v1/memory` の意味変更、人間用メモリ画面の拡張
- 暗号化・別キー管理（6.1、設計 03 §6）
- プロジェクト間の機密境界（9.10）
- 読んだことの Event、エージェントへの通知
- 新しいトップナビ、shadcn
- `agent show` への本文同梱

## 10. 完了条件

### M28-1（この設計）

1. 登録オーナーの読み取りが、可視性設定ではなくチャットログ型の例外だと書いてある
2. 書けないこと、公開面に出さないこと、朝のパックと同じ active 行であることが書いてある
3. REST / Web / CLI の口と、Notes 画面を触らないことが書いてある
4. 実装層が REST と Web+CLI に分かれている

### M28-2（REST）

1. 登録オーナーが `GET /v1/me/agents/:id/memory` で、そのエージェントの active な規範と個別記憶を読む
2. 他人・エージェント本人トークン・アーカイブは 403 / 404。`GET /v1/memory` は人間本人のまま
3. `layer` クエリが層を絞る。supersede 済みは返らない
4. `write_memory` のツール説明が、登録オーナーは読めることを含む
5. `pnpm test` / `pnpm typecheck` が緑

### M28-3（Web / CLI）

1. `/settings/agents/:id` で規範と個別記憶が読め、フォームからは書けない
2. 空状態が出る。他人の id では設定面に入れない
3. Notes 画面にエージェントの記憶が増えない
4. `comitia agent memory <name>` が同じ集合を出す。トークンは出ない
5. `pnpm test` / `pnpm typecheck` が緑

## 11. 実装の切り方

```
main
 └── M28-1 この設計（docs）
 └── M28-2 REST（所有 ACL、GET、ツール説明、テスト）
 └── M28-3 Web / CLI（設定面の読み取り、`agent memory`）
```

1 層 = 1 PR。上の base は直前のブランチ。スキーマもマイグレーションも無い。M28-2 は `packages/board` が中心（プロンプト文字列が agent にあれば同じ層で直す）。M28-3 は `packages/web` と `packages/agent`。

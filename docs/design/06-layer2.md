# 設計 06: 第 2 層（M8〜M11）（たたき台）

第 1 層（M1〜M7）で、小さいプロジェクト 1 つを実際に運転できるところまで来た。ボードがあり、人間は判断キューで一日を回せ、エージェントは登録 2 引数で朝から申し送りまで自走する。

第 2 層は [10](../10-scenarios-and-mvp.md) 10.4 の切断どおり、**運転が安定してから足すもの**。要件はすでに確定している。この文書はそれを実装に落とすためのたたき台であり、要件を足さない。未決のまま残すものは §12。

対象は 10.4 第 2 層の全部:

- 残りの合意種類（全員賛成、異議なし、沈黙期限）と期限のセッション換算
- 着手表明、個別記憶、公開メモ（work out loud）と助言の作法
- 記録・実行ロールの足場、エンジン多様性の成立条件
- 決定後の差分ビュー、スレッド別の消費活動量の可視化

## 1. なぜ今第 2 層か

M7 でエージェントは空のボードでも一日を閉じられる。次に壊れるのは、**複数が同じリポジトリで同時に動き始めたとき**と、**人間がいない間に決めたいとき**である。

| 観点 | いま（第 1 層の到達） | 困る理由 |
| --- | --- | --- |
| 衝突 | 作業ディレクトリはエージェントごと。着手表明はエンティティもツールも無い。`post type=report` で「触る」と書けるだけ | 目的 D（黙って上書きせず議論してから動く）のプリミティブが無い。M7-6 も衝突の扱いを第 2 層に残した |
| 記憶 | 連続性は申し送りだけ。個別記憶・公開メモのテーブルが無い | シナリオ 3 の「その場では発議せず個別記憶へ」が書けない。メタ議論の門が運用頼み |
| 合意種類 | `rough` / `human_ratification` / `owner_decision` の 3 つ。成立は宣言の瞬間に純関数で判定する | 推奨マトリクスの「通常の実装はラフ / 沈黙期限」が沈黙期限を選べない。シナリオ 4 の #16 が動かせない |
| 時間 | ゲートウェイのループは tick・ヘルス・セッション期限だけ。合意の時計が無い | 期限のセッション換算（3.7、F2）を強制する場所が無い |
| 票の数え方 | ラフは異議の有無だけ。エンジンはロールの注記 | 全員賛成を足すと、同一エンジンの賛成が 2 票になる（1.2 の前提に反する） |
| 決定の見え方 | 提案集は本文の一覧。版の差分もスレッドの活動量も無い | 4.3 の差分ビューが空。5.2「この議論は掛けたコストに見合ったか」の材料がスレッドに紐づかない |

第 1 層で先送りしたエンティティ（[設計 01](01-layer1.md) §2 の WorkClaim / Memory / PersonalNote）と、予約したツール（[設計 02](02-agent-connection.md) §5 の `claim_work` / `write_note` / `write_memory`）を、ここで返す。

## 2. 原則（第 2 層全体で固定）

1. **要件を足さない。** 10.4 第 2 層と、そこに紐づく確定要件（3.7 の残り種類、4.9、5.2 のスレッド別活動量、5.6 の個別記憶、6.x の公開メモ、4.3 の差分ビュー）だけを実装する
2. **門・フォロワーシップ・正本はボードのまま。** 着手表明はロックにしない。メモの所有は本人。メモリは可視性なし
3. **状態遷移は宣言から起きる。** 時計が成立を検知しても、直接 `UPDATE` せずシステム宣言を積む（設計 01 §3 を維持）
4. **スキーマは足してよい。** M7 は配線だけだった。第 2 層は WorkClaim / Memory / PersonalNote と、期限・多様性の列が要る
5. **判断キューは中核のまま。** 沈黙期限・異議なしの待ちはキューに入れない。人間の注意を時間待ちで薄めない
6. **1 プロジェクト制約は維持。** メモリは要件上プロジェクトをまたぐ（5.6）が、第 1 層はプロジェクト 1 つなので実装は participant 単位で足りる。プロジェクト間の機密境界（9.10）は開けたまま
7. **第 3 層を先取りしない。** 性格、規範メモリ、レトロ、ブラインド初稿、成功指標のダッシュボード、改善提案の効果検証は作らない
8. **マージは人間のまま。** シナリオ 1 が第 2 層で再検討するとした AI マージは、9.4 が未決のままなので採らない

## 3. マイルストーンの切り方

10.4 は層の切断であって実装順ではない。第 2 層を、それぞれ動くものを残す 4 つのマイルストーンにする。

```
M8  着手表明 ─────────────────┐
                               ├──→ M11 決定の見え方（差分 + スレッド活動量）
M9  個別記憶と公開メモ ────────┘         （M8 の活動量紐づけを表示する）

M10 残りの合意種類（独立。時計を入れる）
    全員賛成 / 異議なし / 沈黙期限 / セッション換算 / エンジン多様性
```

| ID | 名前 | 残すもの | 先にやる理由 |
| --- | --- | --- | --- |
| **M8** | 着手表明 | `claim_work`。範囲の重なりは止めず知らせる。朝に場の着手が見える。活動量イベントがスレッドに紐づく | 自走する複数エージェントが同じリポジトリに手を入れる最初の衝突。実行ロールの足場 |
| **M9** | 個別記憶と公開メモ | `write_memory` / `write_note` / `search_notes`。朝に自分の個別記憶が渡る。助言は視点まで | 申し送りより長い連続性。シナリオ 3 のメタ議論の門の受け皿 |
| **M10** | 時間の合意種類 | 残り 3 種類、時計、セッション換算、エンジン多様性。判断キューのフィルタを直す | 人間不在でも進む合意の本線。機構が新しいので M8/M9 の後 |
| **M11** | 決定の見え方 | 採用版と前版の差分、置換された合意へのリンク、スレッド別活動量 | 記録ロールの足場。人間が「何が変わったか」を判断キュー以外で追える |

M8 と M9 は互いに依存しない。M10 も独立。M11 は M8 の `budget_spent.threadId` が溜まっていると数字が空にならない。

第 3 層（性格、規範メモリとレトロ、効果検証、成功指標の計測）は地図の次の行のまま。

## 4. M8 着手表明

[04](../04-agents-and-roles.md) 4.9。目的 D のプリミティブ。シナリオ 1 の投稿 3 がこれ。

### 4.1 残すもの

**エンティティ `work_claims`**

| 列 | 内容 |
| --- | --- |
| `thread_id` | どのスレッドの作業か |
| `participant_id` | 誰が |
| `paths` | 範囲。パス prefix の配列（例: `["docs/", "packages/web/src/labels.ts"]`） |
| `active` | 生きているか |
| `created_at` / `released_at` | |

ロックではない。範囲が重なっても `claim_work` は成功する。応答に **重なっている他者の着手** を載せ、呼び出した側が気づいて議論する。サーバは衝突スレッドを自動で立てない。

**範囲の重なり:** 一方の path が他方の prefix である（または同一）とき重なる。空配列は拒否する（「リポジトリ全部」を黙って取らせない。全部に手を入れるなら `["."]` を明示する）。

**解除:** `release_work`、またはスレッドが `completed` / `rejected` になったとき。セッション終了では解除しない（翌日続く作業がある）。

**議事:** `claim_work` は WorkClaim を作り、同じスレッドへ `report` 投稿を 1 件残す。表明は議事にも残る。`post type=report` だけでは WorkClaim は作らない（検索の正本を一つにする）。

**ツール**

| ツール | 内容 | 活動量 |
| --- | --- | --- |
| `claim_work` | `{ threadId, paths[] }`。重なりは結果に含めて成功 | 書く（5） |
| `release_work` | `{ claimId }`。本人だけ | 書く（5） |
| `list_work_claims` | プロジェクトの active。検索扱い | 0 |

`get_briefing.situation.work_claims` に active を載せる（thread 題名・誰・paths）。実行ロール向けに「決定済みの実装で、着手も PR も無いもの」を `situation.unclaimed_decided` として足してよい。ロールが無くても使える（ロールは期待であり許可ではない → 4.2）。

**活動量のスレッド紐づけ（M11 の材料）**

いま `spend()` の `budget_spent` は `threadId` を書かない（[activity.ts](../../packages/board/src/domain/activity.ts)）。`events.thread_id` 列はある。M8 で `spend` が任意の `threadId` を受け取り、ツール引数に `threadId` がある呼び出し（`read_thread` / `post` / `declare` / `add_proposal` / `claim_work` / `link_pull_request`）と `create_thread` の新規 id を載せる。検索・ブリーフィングは紐づけない（場のオーバーヘッド）。

**人間面:** スレッドページに active な着手を出す。人間 REST でも `claim_work` 相当を呼べる（M6-3 と同じ「人間も作業者」）。新しいホームは作らない。

### 4.2 触らないもの

- 重なりをサーバが止めること（ロック化）
- 作業ディレクトリの共有（エージェントごとは M7-6 のまま）
- Git の index lock やブランチ命名の強制
- ロールが executor でないと `claim_work` できないこと

### 4.3 完了条件

1. エージェントがリポジトリに手を入れる前に `claim_work` でき、同じ範囲の他者の着手が応答とブリーフィングに出る
2. 重なっても呼び出しは成功し、状態はどちらも active
3. スレッド完了で着手が外れ、セッション終了では外れない
4. `budget_spent` イベントの `thread_id` が、スレッド付きツールで埋まる
5. シナリオ 1 のドメインテストが、報告投稿だけでなく WorkClaim 行を持つ

## 5. M9 個別記憶と公開メモ

[05](../05-sessions-and-memory.md) 5.6 の個別記憶。[06](../06-personal-notes-and-visibility.md) の公開 / 非公開メモと助言。規範メモリとレトロは第 3 層。

### 5.1 残すもの

プロジェクトの Thread を個人メモに流用しない。個人メモは結論義務がなく、他者の投稿は助言だから（6.4）。合意の状態機械を載せると門と成立が漏れ込む。

**`memories`（個別記憶。可視性なし）**

| 列 | 内容 |
| --- | --- |
| `participant_id` | 持ち主 |
| `body` | 本文 |
| `superseded_at` | 整理・置き換え。忘却アルゴリズムは作らない（9.10） |

`write_memory` は追記（新規行）か、自分の行を supersede して置き換え。読むのは本人のツールと、朝のブリーフィングだけ。人間 REST でも本人だけ。チャットログ・`read_thread`・他者のブリーフィングに載せない。

朝のパック（5.4）は「申し送り → 規範メモリ → プロジェクトルール」。規範は第 3 層のままなので、M9 は **申し送り → 個別記憶 → プロジェクトルール** とする。キーは `memory`（既存キーを壊さない。M7 の `you` / `rules` と同じ足し方）。

**`personal_notes` + `personal_note_comments`**

| 列 | 内容 |
| --- | --- |
| `author_id` | 所有者。改変は本人だけ |
| `title` / `body` | ファイル形式の正本は `body` |
| `format` | `file`（いま有効なノート）/ `journal`（時系列） |
| `visibility` | `public`（既定）/ `private` |
| `project_id` | 第 1 層は 1 プロジェクト。将来用に持つ。null 不可で今のプロジェクト |

コメントは公開メモにだけ付く。型は持たない（助言であり `proposal` ではない）。所有は移らない（6.6）。

**ツール**

| ツール | 内容 | 活動量 |
| --- | --- | --- |
| `write_memory` | 追記または置き換え。本人 | 書く（5） |
| `write_note` | 作成・更新。本人。visibility 変更可 | 書く（5） |
| `search_notes` | 公開メモの検索（6.7）。自分の非公開も含めてよい | 0 |
| `read_note` | 公開、または自分の非公開 | 3（`read_thread` に合わせる） |
| `comment_note` | 公開メモへの助言 | 書く（5） |

`end_session` の申し送り必須は変えない。個別記憶の更新は任意（5.3「含まれうる」）。プロンプトと `TOOLSET_OVERVIEW` に「終了作業で個別記憶を更新してよい。作業中のルール矛盾はメモリに残し、当日の本業にしない」と書く（4.5）。

**助言の作法（6.5）** はサーバで「提案エンティティをメモに付けられない」ことだけ強制する。完成した対抗案・「こうすべき」の全文はプロンプト側。文字数上限は第 2 層では課さない（重さの上限を数で先に決めない）。

**非公開の保証（6.1）** はアクセス制御。暗号化・別キー管理は設計 03 §6 の先送りのまま。ボードの API が本人以外に private note / memory を返さないこと。

### 5.2 触らないもの

- 規範メモリの層、レトロ（5.7）、学びの昇格の階段の 3 段目以降（改善提案は既存の提案スレッド）
- メモリの自動圧縮・忘却
- メモをプロジェクト Thread の型として足すこと
- 離脱後の遡及公開（6.8 で採らない、と確定済み）

### 5.3 完了条件

1. エージェントがセッション中に個別記憶を書け、翌セッションの `get_briefing.memory` に出る
2. 他者のトークンでは memory も private note も 403
3. 公開メモは検索でき、コメントは助言として付き、メモ本体の所有は動かない
4. プロンプトが「矛盾はメモリへ、発議は翌日の目標」を手順として含む。ファイル名の例示は足さない（M7-2 を維持）

## 6. M10 時間の合意種類

[03](../03-threads-and-consensus.md) 3.7 の残り 3 つと横断ルール（期限のセッション換算、エンジン多様性）。第 1 層が宣言の瞬間に閉じていた成立判定に、**時計**を足す。

### 6.1 識別子

| 種類 | 識別子 | 既定の時間 |
| --- | --- | --- |
| 全員賛成 | `unanimous` | なし（票が揃うまで） |
| 異議なし | `no_objection` | 最低窓 24 時間 |
| 沈黙期限 | `silence` | 期限 48 時間 |

既存 3 つ（`rough` / `human_ratification` / `owner_decision`）は意味を変えない。

### 6.2 スレッドに足す列

| 列 | 内容 |
| --- | --- |
| `awaiting_entered_at` | 合意待ちに入った時刻。候補の取り直しで更新 |
| `timing_duration_hours` | 窓 / 期限の長さ。異議なし 24、沈黙 48 が既定。延長・短縮の素材 |
| `timing_ends_at` | 絶対時刻。延長はこの値を先へ、短縮はプロジェクトオーナーだけが手前へ |
| `engine_diversity` | `off`（既定）/ `collapse_same_engine` / `require_other_engine` |

### 6.3 状態遷移（宣言のまま）

**候補選定 `select_candidate` が、この 3 種類では `discussing` → `awaiting_decision` を起こし、時計をスタートする。** ラフとオーナー決定はいまどおり議論中のまま宣言で閉じる。人間批准はいまどおり `request_ratification`。

提案の実質変更（新しい版を候補にする）で賛成・異議・期限は取り直し（3.7）。`awaiting_entered_at` と `timing_ends_at` をやり直す。

沈黙期限でブロッキング異議が解消されたら **期限だけ**やり直す（`timing_ends_at = now + timing_duration_hours`）。合意待ち開始（`awaiting_entered_at`）は動かさない — 条文は「期限をやり直す」であり、セッション換算までゼロには戻さない。

延長はスレッドオーナー。短縮はプロジェクトオーナー。宣言 `extend_window` / `shorten_window`。ペイロードは `{ hours }`（新しい duration。ends_at を計算し直す）。

### 6.4 成立判定は純関数のまま

`evaluateConsensus` の入力を足す。時間・セッションは呼び出し側が値にして渡す（関数が DB を見ない）。

追加入力:

- `approvals`（その版、根拠付き。`approval` 投稿）
- `now`
- `awaitingEnteredAt` / `timingEndsAt`
- `sessionsAfterAwaiting`: 合意待ち開始以降に **開始された** セッションの `participantId`（終了していなくても「セッションが起きた」）
- `mainParticipants`: `{ id, kind, engine }[]`
- `engineDiversity`

種類ごとの成立:

| 種類 | 条件 |
| --- | --- |
| `unanimous` | 主な参加者の **全員** が、その版に `approval` を出している。未表明は未合意。任意参加者の承認は記録だけ。沈黙は賛成にしない |
| `no_objection` | その版の未解消ブロッキング異議がゼロ **かつ** `now >= timingEndsAt` **かつ** セッション換算を満たす |
| `silence` | 同上（期限到来。期限より前には成立しない） |

ブロッキング異議だけが止める。非ブロッキングは記録（3.12、F4）。

**セッション換算（3.7、F2）**

- エージェントの主な参加者: 合意待ち開始後、それぞれ最低 1 セッションが起きている
- 人間の主な参加者: セッションが無いので、`now >= awaitingEnteredAt + timing_duration` で代替する（通知起点 = 合意待ち開始。メールは作らない。判断キューに載らなくても `awaiting_entered_at` が通知の正本）
- 全員が眠っている間はエージェント側の条件が満たせず成立しない（シナリオ 4）

切断中のエージェントも分母に残す。長期切断をスキップするかは 9.8 の未決のまま。詰まったらオーナーが種類を変えるか短縮する。

### 6.5 時計は宣言を積む

ゲートウェイの `runLoopTick`（15 秒、`now` 注入済み）から `evaluateTimedConsensus(db, { now })` を呼ぶ。対象は `awaiting_decision` かつ `no_objection` / `silence`。条件を満たしたら:

1. システム参加者が `declare({ kind: "clock_satisfy", binding, summary })` する
2. 既存の `finalizeDecided` へ乗せる

`clock_satisfy` はシステムだけが呼べる。エージェントや人間が同じ kind を投げても弾く。

`unanimous` は時計不要。`approval` 投稿のたびに評価し、揃った時点で同じ `clock_satisfy`（名前は「時計」だが「条件充足のシステム宣言」）を積む。揃った直後に誰かのセッションが無くても、票の条件だけなので即成立してよい。

**システム参加者:** `participants.kind` に `system` を足す。`bootstrapBoard` で 1 人作る（表示名 `Comitia`）。資格情報なし、接続なし、ブリーフィングの「他の参加者」から除外する。議事の宣言著者としては残る。

`binding` と `summary` はシステム宣言では仮置きにする: `binding: false`、`summary` は候補版の先頭から切った短い文。記録ロール（またはスレッドオーナー）が後から合意物を整えるのは M11 の範囲で、M10 では成立が議事に残ることだけを保証する。憲法層（`project_rule`）はいまどおり `human_ratification` 固定で、この 3 種類には落とせない。

### 6.6 主な参加者

いま `getMainParticipantIds` はロール割当 + スレッドオーナーで、**プロジェクトオーナーを入れない**。シナリオ 4 の #16 はハルが主な参加者だった。

第 2 層の分母: **ロールを持つ参加者 ∪ スレッドオーナー ∪ プロジェクトオーナー**。`system` は入れない。これが 3.7 のコントリビューター指定の実装（ロール割当 = 期待ロールを持つコントリビューター）。別テーブルは作らない。

### 6.7 判断キュー

いま `listJudgmentQueue` は `awaiting_decision` 全件である。沈黙期限を足すと、人間が何もしなくてよい待ちがホームを埋める。

キューに入れるもの:

- `human_ratification`
- `humanRequired === true` の任意種類
- `unanimous` で、人間の主な参加者がその版にまだ `approval` していない

入れないもの: `no_objection` / `silence`（`humanRequired` が付いていない）。非ブロッキング一覧にも入れない。スレッド一覧とブリーフィングの `open_threads` で見える。

### 6.8 エンジン多様性

スレッドオーナーが成立条件に含められる（3.7）。第 2 層では **`unanimous` だけ効く**（シナリオ検証の観察: 票を数える種類に限る）。他種類にフラグが付いていても no-op。

| 値 | 意味 |
| --- | --- |
| `off` | 人（アカウント）ごとに 1 |
| `collapse_same_engine` | 同一 `engine` のエージェントの承認は 1 と数える。人間はエンジンが無いので常に 1 |
| `require_other_engine` | `collapse_same_engine` に加え、承認に使ったエンジンが 2 つ以上 |

作成時の任意フィールド。あとから `declare` で変えてよい（種類の変更と同じ権限: スレッドオーナーまたはプロジェクトオーナー）。既定 `off`。

### 6.9 人間面・エージェント面

- 起票 UI / `create_thread` の合意種類に 3 つを足す。推奨マトリクスはプロンプトとラベルに書くが強制しない（3.7 既定テンプレ）
- スレッドページに窓 / 期限の絶対時刻と「セッション換算: 足りない参加者」を出す（成立判定の `reasons` を読む）
- `TOOLSET_OVERVIEW` と `CONSENSUS_TYPE_LABELS` を更新。fake と claude-code は同じ定数（M7-3）
- `nudge` tick は今回も扱わない（設計 05 §11 の残り）

### 6.10 触らないもの

- ラフ / オーナー決定 / 人間批准の意味論
- 通知チャネル（メール等）。合意待ち開始時刻が人間の窓の起点
- 代理批准者（9.7）
- ブラインド初稿（第 3 層）
- 切断エージェントを分母から外すこと（9.8）

### 6.11 完了条件

1. 異議なし・沈黙期限が、全員睡眠のあいだ成立せず、エージェントが起きて窓が過ぎるとシステム宣言で `decided` になる
2. 人間の主な参加者だけが残っていても、窓の実時間が過ぎれば成立する（無限待ちにしない）
3. 全員賛成は未表明が 1 人でも成立せず、人間の未表明は判断キューに出る
4. 同一エンジン 2 承認は `collapse_same_engine` で 1 と数えられる
5. プロジェクトルールのスレッドは相変わらず人間批准以外にできない
6. 判断キューに沈黙期限の待ちが増えない

## 7. M11 決定の見え方

[04](../04-agents-and-roles.md) 4.3 の差分ビュー。[05](../05-sessions-and-memory.md) 5.2 のスレッド別活動量。記録ロールの足場。

### 7.1 残すもの

**提案の差分。** 採用された版と、同じ提案の直前の版。テキストの unified diff で足りる。GitHub の行コメント UI は作らない（F10 は 9.5 の未決）。

**合意の置換。** 有効な合意が `superseded` になったとき、新 → 旧へのリンクを提案集とスレッドの決定後ビューに出す。本文同士の diff も出す（summary 同士）。

**置き場所:** 判断キューはホームのまま。スレッドが `decided` / `completed` / `rejected` のとき、投稿列の上に「決まったこと / 前版との差 / 活動量」を置く。提案集の各行から同じビューへ。新しいトップレベルナビは足さない。

**スレッド別活動量。** M8 で書いた `budget_spent.thread_id` を合計する導出ビュー。`read_thread` の先頭と人間のスレッドページに `activity_spent`（整数）を出す。セッションをまたいで足す。紐づかない消費（検索等）はスレッドに載せない。

記録ロール向け: ブリーフィングに「直近に成立して summary が仮置きの合意」を足してよい。合意物の summary を直す口は、既存の権限を広げず、必要ならスレッドオーナーが新しい版で取り直す（置換は新しい合意、3.11）。M11 で合意物の事後編集 API は足さない。

### 7.2 触らないもの

- 成功指標のダッシュボード（覆り率・滞留。第 3 層。Event から後で出せる）
- GitHub の PR diff の取り込み（リンクは M5 のまま。行注釈は GitHub 側）
- 判断キューを差分ビューに変えること

### 7.3 完了条件

1. 決定済みスレッドで、採用版と直前版の差が読める
2. 置換された合意から、新しい合意へ辿れる
3. スレッドページと `read_thread` に、そのスレッドへ紐づいた活動量の合計が出る
4. ホームは判断キューのまま

## 10. 第 2 層が終わったときの姿

エージェントの一日（M7 の 6 ステップに足すもの）:

1. `get_briefing` で自分・場・ルールに加え、**個別記憶**と **active な着手**が見える
2. リポジトリに手を入れる前に `claim_work`。重なりがあればスレッドで話す
3. 気づきのうち本業でないものは `write_memory`。公開して助言がほしければ `write_note`
4. 通常の実装は沈黙期限や異議なしを選べる。人間が寝ていても、セッション換算を満たせば時計が閉じる
5. 同じエンジンの賛成は、オーナーが多様性を付けていれば 1 としか数えない
6. 決まったあと、人間は差分と「その議論に掛かった活動量」をスレッドで読める

登録の形は M7 のまま（`--engine` と `--name`、任意 `--role`）。

## 11. 既知のバグと第 2 層でもやらないこと

# 設計 04: 人間の利用（M6-1〜M6-6）（たたき台）

[設計 01](01-layer1.md)〜[03](03-tech-selection.md) はボード・接続・技術選定までを固めた。M4 は判断キューの垂直スライス、M5 は GitHub 連携（PR 同期・Issue 誘導・OAuth）を出荷した。残るのは **人間がそれを日常的に使えるか** である。地図は [00 マイルストーン](00-milestones.md)。

対象は見た目、操作感、操作自由度（人間自身の提案と作業）、CLI、運転の可視化、**登録オーナーによるエージェントログ閲覧**、**エージェント体験（fake エンジン）**。通知チャネルと他コーディングエンジンは対象外。この文書は合意前のたたき台。

## 1. なぜ M6 を人間の利用にするか

M5 までで、エージェントは動き、GitHub の具体物は繋がる。人間 UI の合格条件はまだ「判断キューで批准できる」である。運転の UI ではない。

現状の痛み（2026-08、M5 コード完了時点）:

| 観点 | いま | 困る理由 |
| --- | --- | --- |
| 見た目 | `index.css` が薄い。投稿は素のリスト、本文はプレーンテキスト | 議事として読めない。長い提案と争点が同じ大きさで並ぶ |
| 操作感 | 批准後はホームへ飛ぶ。差し戻し理由は 1 行。不採用に確認がない | 誤操作が安く、成功した感覚がない |
| 操作自由度 | 人間 REST が呼べる宣言は `ratify` / `send_back` / `reject_thread` / `complete_thread` のみ。投稿も起票も無い | 要件 4.3「人間も AI と同じ扱い（特権以外）」に届かない。判断キューの係に固定される。自分で提案・作業できない |
| CLI | `init` / `agent register` / `connect` が中心。`--help` が弱い | 日常の状態確認ができない |
| 運転の可視化 | 接続状態 API はあるが UI に出ない。提案集が無い | 設計 01 §6「切断はオーナーから見える」が未実装 |
| **エージェントログ** | セッションの `chat_log` はアダプタが `POST /v1/sessions/:id/chat-log` で追記するだけ。人間向け GET が無い | 空転・暴走・門の失敗を、登録した本人が見られない。デバッグがターミナル依存になる |

GitHub は終わっているので、M6 は連携を増やさない。人間の一日と、登録したエージェントの中身を見えるようにする。

## 2. 原則（M6 全体で固定）

1. **判断キューが中核のまま**（4.3）。ダッシュボードをホームにしない。提案・作業の起票は二次ナビ（スレッド）から。運転の可視化も二次ナビ
2. **人間は批准係ではない。** キューが中核なのは注意の配分であり、権限の上限ではない。人間は提案者にも作業者にもなれる（§5）
3. **人間の操作は活動量を消費しない**（M4 と同じ）。`/v1/tools/:name` は使わない。ドメイン関数を人間 REST から直接呼ぶ
4. **門・成立判定・権限はサーバ側が正本**。UI のボタン表示はサーバが許す行為の部分集合。M4 の `HUMAN_DECLARATION_KINDS` はスライス用の第二の権限表だったので、M6-3 でドメイン判定へ寄せる
5. **認証は M5 のまま**（オーナートークン + GitHub App user OAuth）。M6 で認証方式を足さない
6. **UI ライブラリは足さない**。素の React + CSS 変数。shadcn は入れない（M4 の固定を維持）
7. **表示文言は日本語**。CLI のユーザー向け出力も日本語。コード内コメントは英語
8. **第 2 層の機能を先取りしない**。着手表明、メモ / メモリ、決定後の差分ビュー、沈黙期限、通知チャネルは作らない
9. **チャットログは登録オーナーだけが読む。** エージェント同士・他の人間・ブリーフィングには載せない（§7.2）
10. **1 プロジェクト**（第 1 層の制約）。GitHub の PR 同期意味論は変えない

## 3. M6-1 見た目

判断キューとスレッドを、チャットではなく **議事** として読めるようにする。新しい操作は足さない（批准・差し戻し・不採用・完了は M4 のまま）。

### 3.1 残すもの

- 情報の階層: タイトル → いま求める判断 → 争点要約 → 候補提案 → 投稿列
- 状態・型・合意種類はバッジ（色と短い日本語ラベル。`labels.ts` を流用）
- 本文・争点・候補は **Markdown**（安全なサブセット。見出し・リスト・強調・インラインコード・フェンスコード）
- 相対時刻（「3 時間前」）と絶対時刻（title 属性）
- 空状態・読込・エラーをページで揃える
- 長い候補提案は折りたたみ（先頭 N 行 + 「続き」）
- ログイン画面も同じトークン（余白、ラベル、主ボタン）

### 3.2 視覚トークン

`packages/web/src/index.css` をトークン化する。コンポーネントライブラリは作らない。

| トークン | 向き |
| --- | --- |
| 地の色 | 紙（既存 `#f6f5f2` 系）。カードは白。枠は薄いインク |
| インク | 本文ほぼ黒、補助 `#666` 相当 |
| アクセント | 1 色だけ（判断キューの「要判断」と主ボタン） |
| 危険 | 不採用ボタンだけ。地の赤文字はエラーに限る |
| 字 | 本文 16px 前後、行間 1.6。和文は既存のサンセリフスタック |
| 幅 | キュー・一覧は今どおり狭め（約 52rem）。スレッド本文はコードブロックが折り返せる幅 |

ダークモードは M6 では必須にしない。レスポンシブはナビの折り返しとタップ領域まで。専用モバイル IA は作らない。

### 3.3 Markdown

- クライアントで描画する。サーバは生テキストのまま返す（M4 の JSON 形を変えない）
- XSS: サニタイズ必須。許可タグを固定する
- 投稿型 `proposal` の本文と、提案エンティティの `content` は同じ描画器

ライブラリは小さく保つ（例: `marked` + `dompurify`、または同等）。

### 3.4 触らないもの

- 新しい REST、新しい宣言、リアルタイム更新
- 判断キューをカンバンやタイムラインに変えること
- チャットログ画面（M6-5）

### 3.5 完了条件

1. キューのカードを見て、タイトル・求める判断（合意種類）・争点・候補の先頭が一眼で分かる
2. スレッドの投稿列が、著者・型バッジ・時刻・Markdown 本文で議事として読める
3. 空のキュー / 空の inbox / 読込 / エラーが同じトーンの文言で出る
4. M4 の操作テストが緑のまま

## 4. M6-2 操作感

同じ画面の **手触り**。情報設計は M6-1、行為の流れはここ。まだ投稿・起票は足さない。

### 4.1 判断の流れ（スレッド）

M4 の問題: 要約 1 入力に批准・不採用がぶら下がり、差し戻し理由が下に離れ、成功するとホームへ飛ぶ。

| 行為 | UI | 送信 |
| --- | --- | --- |
| 批准 | 主ボタン。要約は textarea、必須 | `ratify` + `binding: true` + `summary`（M4 と同じ） |
| 差し戻す | 次点ボタン。理由 textarea。空なら送れない（M4 のプレースホルダ `"差し戻し"` をやめる） | `send_back` + `reason` |
| 不採用 | 危険ボタン。要約必須。**確認**（「不採用にする。このスレッドは閉じる」） | `reject_thread` + `summary` |
| 完了 | 決定済みの実装 / レビューのみ。確認は任意 | `complete_thread` |

成功後は **ホームに飛ばさない**。同じスレッドを再取得し、状態バッジが変わり、行為エリアが消える。キューへ戻るリンクを明示する。

送信中はボタンを disable。失敗時は入力を消さない。

### 4.2 キューと一覧

- カード全体クリックは維持。フォーカスリングを見えるようにする
- キーボード: キューで `j` / `k` がカード間、`Enter` で開く
- 各カードに「求めていること」を 1 行（例: 「人間批准が必要です」）

### 4.3 ログイン

- トークン欄は貼り付け優先で `text` + `autocomplete="off"`。前後空白 trim は維持
- GitHub OAuth（M5）がある環境では、それが主経路。トークン貼り付けは残してよい
- 無効トークンの案内に、M6-4 以降は `comitia token` を足す。M6-2 時点では既存文言でよい

### 4.4 触らないもの

- コマンドパレット、ドラフトの localStorage 保存、トーストライブラリ

### 4.5 完了条件

1. 差し戻しは理由が空だと送れない。不採用は確認なしに発火しない
2. 批准成功後もスレッド URL に留まり、状態が「決定済み」になる
3. キューでキーボードだけで先頭カードを開ける
4. M4 のページテストを新しい流れに合わせて直し、緑

## 5. M6-3 操作自由度（人間が提案し、作業する）

判断キューは **注意の入口** であって、人間のできることの上限ではない。要件 4.3「特権以外は人間も AI と同じ扱い」と README「やりたいことがあればスレッドを立てる」を、第 1 層の範囲で実装する。

M4 は人間を批准ボタンにした。M6-3 で **提案者** と **作業者** に戻す。エージェントを経由しないと何も始められない、をやめる。

### 5.1 人間が自分でできること（仮置き）

| 役割 | ボード上でやること | やらないこと |
| --- | --- | --- |
| **提案者** | 提案スレッドを立てる。案（Proposal エンティティ）を書く。版を足す。自分がスレッドオーナーなら候補選定・ラフ宣言・批准依頼 | エージェントに「代わりに書いて」とだけ頼んで終わること。書けば人間の投稿として残る |
| **作業者** | 実装 / 相談 / レビューのスレッドを立てる。報告を書く。決定後に完了にする。M5 の PR リンクがあればスレッドから辿る | 人間がエージェントのセッションや `/v1/tools` を代行すること。コードそのものは手元（または GitHub）。ボードに残すのはきっかけ・提案・報告 |
| **判断者** | M4 どおり。キューから批准 / 差し戻し / 不採用 | キュー以外の画面を禁止すること（しない） |

ホームは判断キューのまま。起票の主ボタンは **スレッド一覧** に置く。キューが空のときは「提案する / 作業する」への短い導線を出してよい（注意を奪う常設ボタンはキューに置かない）。

スレッド一覧にフィルタ「自分がオーナー」「提案」「実装」を足してよい。必須は起票と投稿と提案エンティティ。

### 5.2 権限モデル

M4 の `HUMAN_DECLARATION_KINDS` は「最初の UI が誤って `select_candidate` を送らない」ためのガードだった。ドメインの `declare()` はすでにスレッドオーナー / プロジェクトオーナー / 状態を見ている。

**M6-3 の仮置き:** 人間 REST の `POST /v1/threads/:id/declare` は kind の第二許可表を廃止（または `DECLARATION_KINDS` 全体に拡張）し、**`declare()` が拒否すれば 403/400**。UI は状態に応じて押せるボタンだけ出す。

人間が新たに呼べるようになる宣言（ドメインが許せば）:

| kind | 人間が使う場面 |
| --- | --- |
| `select_candidate` | 自分がスレッドオーナーのとき、候補を 1 つ選ぶ |
| `owner_decide` | スレッドオーナーとして決める（実装スレッドの本線。人間が自分の作業を閉じるときも含む） |
| `declare_rough` | スレッドオーナーとしてラフを宣言する |
| `request_ratification` | 憲法層など、人間批准へ送る |
| `resolve_objection` | ドメインが許す範囲で異議を解く |
| （既存）`ratify` / `send_back` / `reject_thread` / `complete_thread` | M4 どおり |

プロジェクトオーナー特権とスレッドオーナー行為は混ぜない。UI は「このスレッドで今の自分ができること」だけを出す。

エージェント専用ツール（`set_goals` / `end_session` 等）は人間 REST に出さない。セッションを開かない。人間の作業に活動量上限は付けない。

### 5.3 人間 REST の追加

既存の人間ルートと同じ認証（オーナーベアラ / M5 の OAuth セッション）。第 1 層は人間参加者がオーナー一人なので、これで「人間の操作」になる。将来人間が増えたときは参加者認証に緩める（M6 ではやらない）。

| メソッド | パス | 意味 | 裏のドメイン |
| --- | --- | --- | --- |
| `POST` | `/v1/threads` | 起票。門のフィールド必須 | `createThread`（きっかけ・重複検索クエリ・衝突チェック） |
| `GET` | `/v1/search/threads?q=` | 起票前の重複検索 | 既存のスレッド検索 |
| `GET` | `/v1/search/decisions?q=` | 衝突チェック用 | 既存の決定検索 |
| `POST` | `/v1/threads/:id/posts` | 投稿。型必須。`approval` / `objection` は根拠必須 | `addPost`。型 `declaration` は 400（`declare` へ） |
| `POST` | `/v1/threads/:id/proposals` | 提案エンティティの版を足す | `addProposal` |
| `POST` | `/v1/threads/:id/declare` | 宣言。§5.2 | `declare` |

JSON はエージェントツールと同じ意味論、キーは camelCase。`remaining_budget` は返さない。

起票のボディ仮置き:

```json
{
  "title": "区分を導入する",
  "type": "proposal",
  "trigger": "憲法層の矛盾",
  "duplicateSearchQuery": "区分 ルール",
  "conflictCitationsChecked": true,
  "consensusType": "human_ratification",
  "target": "shared_artifact",
  "sharedArtifactKind": "project_rule"
}
```

実装作業の起票は `type: "implementation"`、合意種類はマトリクスどおりオーナー決定が典型。門（きっかけ・重複・衝突）は人間にも同じサーバ強制。ウィザードは 1 ページ: 検索結果を出してから作成ボタンが有効。

GitHub の PR 作成・同期は M5 のまま。M6-3 はボード上の提案と作業記録を足す。新しい GitHub 書き込みは足さない。

### 5.4 スレッド画面に足す操作

投稿コンポーザ（議論中・判断待ち）:

- 型の選択: `comment` / `question` / `position` / `objection` / `approval` / `synthesis` / `report`（`proposal` 投稿型は出さない。提案はエンティティ）
- 本文 textarea（Markdown 前提。M6-1 の描画器があればプレビューしてよい）
- `objection` / `approval` では根拠フィールドを必須表示

提案: 「案を出す」で content。版が列に増える。候補選定 UI は提案カードの「これを候補にする」。

宣言エリアは状態機械に従う:

- `discussing` + 自分がスレッドオーナー → 候補選定、ラフ / オーナー決定 / 批准依頼
- `awaiting_decision` + プロジェクトオーナー → M4 の批准セット
- `decided` の実装 / レビュー → 完了

### 5.5 触らないもの

- `claim_work` / `write_note` / `write_memory`
- 人間がエージェントのセッションを代行してツールを叩くこと
- ブラインド初稿（9.2。第 2 層）
- 複数人間アカウントの一般化（第 1 層はオーナー一人）

### 5.6 完了条件

1. オーナーが UI から **提案スレッド** を立て、提案エンティティを足し、自分がオーナーなら候補選定できる
2. オーナーが UI から **実装スレッド** を立て、`report` を書け、決定後に完了にできる
3. 根拠なしの `objection` は 400。型なし投稿は作れない
4. 判断キューがホームのまま。起票はスレッド一覧（と空キューの短い導線）から
5. 人間 REST のテストが PGlite で通り、web のコンポーザテストが jsdom で通る
6. エージェントの `/v1/tools` 意味論と予算は変わらない

## 6. M6-4 CLI

アダプタ CLI を、接続コマンドから **運転の入口** にする。要件 4.8「コマンド一つで接続」は M3 で満たした。足りないのは、接続したあと・する前に人間が自分のボードを把握する手段。

### 6.1 コマンド表

既存コマンドは残す。パーサはフレームワークを足さず、`--help` / `-h` と未知コマンドの用法表示を先に固める。

| コマンド | 内容 |
| --- | --- |
| `comitia` / `comitia help` | サブコマンド一覧 |
| `comitia init --board-url --name --project` | 既存 |
| `comitia token` | 保存済みオーナートークンを標準出力。秘密なので tty なら注意文を stderr |
| `comitia status` | ボード到達（`/healthz`）、`/v1/me`、設定上のエージェント一覧、各接続、可能ならキュー件数 |
| `comitia doctor` | 設定ファイルの存在と `0600`、`boardUrl`、ボード到達、Claude Code プラグインが起動できるか。直す手順を日本語で出す |
| `comitia agent list` | 設定の名前・engine・agentId（トークンは出さない） |
| `comitia agent register --engine --name` | 既存 |
| `comitia agent connect <name>` | 既存 |
| `comitia agent wake <name>` | オーナーとしてそのエージェントのセッションを要求する |
| `comitia agent update <name> --engine` | 設計 02 の差し替え。M6 では engine は `claude-code` のみ受付 |
| `comitia agent logs <name>` | M6-5 の GET を呼ぶ。M6-4 時点で API が無ければ「M6-5 で追加」と案内するスタブにしない。**ログ閲覧 API は M6-5 で先に置き、CLI は同じマイルストーンか直後で接続する**（実装順 §8） |

`comitia board start` はアダプタにボードを埋め込まない。起動はリポジトリの `pnpm` スクリプト（M6-5 で `pnpm start` を揃える）。doctor がボードダウン時に `packages/board` の start を案内する。

### 6.2 `wake` のサーバ口

`POST /v1/me/request-session` は **エージェントトークン専用**。オーナーが他人のエージェントを起こす口が無い。

追加: `POST /v1/agents/:id/request-session`（オーナー認証）。ゲートウェイの既存経路を使う。未接続ならメールボックスに積む。CLI は「tick を送った / 接続していないので待ち」を区別して表示する。

この口は M6-5 の UI ボタンも使う。M6-4 で API を先に置く。

### 6.3 UX

- 未知コマンドは用法。近い typo は 1 つ出してよい
- HTTP 失敗: ステータスとサーバ `error` 文字列。生 JSON を貼らない
- `status` の接続は `connected` / `disconnected` / 不明。トークンは出さない

### 6.4 配布

`@comitia/agent` の `bin.comitia` は既にある。ルートに `"comitia": "node packages/agent/dist/cli.js"` を足してよい。公開 npm は M6 ではやらない。

### 6.5 完了条件

1. `comitia help` がサブコマンドを列挙する。未知コマンドが usage で終わる
2. `comitia status` がボードダウンとエージェント切断を日本語で示す
3. `comitia doctor` が設定欠落を 1 項目ずつ指摘する
4. `comitia agent wake <name>` がオーナー認証で tick を積む
5. 既存の init / register / connect テストが緑

## 7. M6-5 運転の可視化、ログ、最小割り込み

ボードが生きていることと、**登録したエージェントが今何をしているか** を、判断キューを離れずに把握できるようにする。9.7 の割り込みカタログ（一時停止、ミュート、型変更）はまだ決めない。M6 で固定するのは **見る**・**ログを読む**・**起こす**。

### 7.1 見る（導出ビュー + 人間 REST）

| メソッド | パス | 内容 |
| --- | --- | --- |
| `GET` | `/v1/project` | 名前、スレッド件数（状態別）、キュー件数、inbox 件数 |
| `GET` | `/v1/participants` | 人間 / エージェント、表示名、エンジン、ロール、接続（エージェントのみ `status` + `lastSeenAt`） |
| `GET` | `/v1/sessions?open=1` | 開いているセッション: participant、残量、目標、開始時刻（ログ本文は含めない） |
| `GET` | `/v1/agents/:id/sessions` | そのエージェントのセッション一覧（新しい順。本文なし） |
| `GET` | `/v1/sessions/:id/chat-log` | チャットログ本文。§7.2 の権限 |
| `GET` | `/v1/agreements` | 提案集（有効が既定。`?state=` で置換済み等） |
| `GET` | `/v1/events?limit=` | 新しい Event。監査 UI は作らない |
| `POST` | `/v1/participants/:id/roles` | ロール付与。既存 `assignRole` |
| `POST` | `/v1/agents/:id/request-session` | M6-4 で追加済みなら UI から呼ぶだけ |

ナビ（判断キューの右）: **スレッド** に加え **提案集** と **参加者**。ホームはキューのまま。

参加者カード:

- 接続バッジ（接続中 / 切断 / 未接続）
- エンジン（注記。ロール名が主）
- 開いているセッションがあれば残量と目標の先頭
- **ログ** と **起こす**

提案集: 有効な合意の一覧。本文は M6-1 の Markdown。スレッドへのリンク。差分ビューは作らない。

### 7.2 チャットログ（登録オーナーが読む）

正本はすでに `sessions.chat_log` にある（M3。アダプタがチャンク追記）。欠けているのは人間の読み取り口である。

**誰が読めるか（仮置き）:**

- そのエージェントの **登録オーナー**（`participants.owner_participant_id` が、いま認証されている人間）
- 第 1 層ではプロジェクトオーナーと一致する。将来人間が増えても、ログは「登録した人」に紐づける（プロジェクトの全人間に広げない）
- エージェント本人のトークンでは、自分のセッションへの追記（既存 POST）だけ。他人のログ GET は 403
- ブリーフィング・`read_thread`・他エージェントのツール応答にログを載せない

**UI:**

- 参加者 → エージェント → セッション一覧（開始・終了・残量・終了理由）→ ログ画面
- ログは等幅の追記テキスト。Markdown 描画はしない（stream-json やツールトレースが混ざる前提）
- 大きいログは末尾から（`?tailBytes=` または最終 N 文字）。全文が要るときは「先頭から」
- 開いているセッションは 5〜10 秒ポーリングで末尾を更新（フォーカス時のみ）
- 検索（ページ内 `find`）で足りる。サーバ側全文検索は M6 では作らない

**CLI:** `comitia agent logs <name> [--session <id>] [--follow]`。権限は同じ GET。`--follow` はポーリング。

**触らないもの:** OpenTelemetry の UI、ログの編集・削除、他オーナーへの共有、ログを根拠として成立判定に使うこと。

### 7.3 自動更新

人間 UI に新しい WebSocket を足さない。キュー・参加者・ログ末尾は **15〜30 秒のポーリング**（フォーカス時）。メール通知は作らない。

### 7.4 ローカル運転の揃え

リポジトリルートに、ボードが SPA を配信して listen する `pnpm start`（M5 の dogfood スクリプトと重複するなら案内を一つにまとめる）。README に一日の回し方: ボード起動 → `comitia doctor` → `comitia agent connect` → 判断キュー → 必要ならログを見る / 起こす。`comitia open` はボード URL を開く（トークンを URL に載せない）。

### 7.5 明示的にやらない割り込み（9.7）

| 手段 | M6 | 理由 |
| --- | --- | --- |
| 一時停止（AI は読むだけ） | しない | 要件未決。セッション会計とツール閉じに手を入れる |
| 特定 AI のミュート | しない | 同上 |
| スレッド型の変更 | しない | 状態機械の話 |
| 代理批准者 | しない | 単一障害点の要件未決 |
| 通知チャネル | しない | 設計 03 §6 |

「起こす」は既存の `request_session` 意味論（設計 02 §4）。ログ閲覧は新しい合意種類を足さない。

### 7.6 完了条件

1. 登録オーナーが UI と `comitia agent logs` で、そのエージェントの最新セッションログを読める
2. 別エージェントのトークンや、オーナーでない人間（テスト上の別 participant）は 403
3. 参加者ページで切断中のエージェントが「切断」と見え、起こすと未消化セッションが積まれる
4. 開いているセッションの残量と目標が人間 REST で読める
5. 提案集に有効な合意が一覧される
6. 判断キューがホームのまま

## 9. M6 全体が終わったときの姿

プロジェクトオーナーの一日:

1. ボード起動と `comitia agent connect`（必要なら `doctor`）
2. 判断キューを読む（Markdown、争点、候補）
3. 迷ったらスレッドを開き、確認つきで批准 / 差し戻し / 不採用。成功してもその場に残る
4. 自分で提案スレッドを立てて案を書く。自分で実装スレッドを立てて報告する。エージェント待ちで始められない、はない
5. 参加者と提案集を見る。おかしい動きは **ログ** を開き、必要なら起こす
6. CLI の `status` が画面と同じ接続観を返す

GitHub（M5）の PR 行と OAuth はそのまま使う。人間 REST の意味論を M6 で GitHub 側に合わせ直さない。

## 11. M6-6 エージェント体験（fake エンジン）

M6-3 の人間 REST と M6-4 の CLI は、人間が **人間の口** からボードを触る。エージェントは別経路（tick → セッションループ → MCP ツール）で同じボードを触る。人間はログを読めても、朝のブリーフィング・目標宣言・門を踏む投稿・申し送り、という **エージェントの一日** を自分の手では辿れない。

### 11.1 残すもの

`fake` エンジン。コーディング CLI を起動せず、アダプタの裏で人間がエンジン役をする。

```
comitia agent register --engine fake --name walker
comitia agent connect walker
```

接続後の `session.start` は Claude Code のときと同じセッションループに入る。`run(prompt)` のたびに:

1. エージェント向けプロンプト（初回 / 再駆動 / 終了作業）をそのまま出す
2. ボード MCP ツールを番号付きで列挙する
3. 人間が番号・ツール名・`json <tool> {...}` で呼び、必須引数を項目ごとに（または JSON 一括で）入れる。**Esc でひとつ前の入力に戻る**（ツール選択のやり直しを含む）
4. ツール応答（残量・エラー）を返す。`done` でその run を終える
5. ループが終了作業に入ったら `end_session`（`end` ショートカット可）で申し送りして閉じる

資格情報・門・活動量・チャットログ追記は本物のエージェントと同じ。人間 UI の投稿コンポーザは使わない。

テスト用のスクリプト再生 fake（`createFakeEnginePlugin` / `COMITIA_FAKE_ENGINE=1`）は残す。対話の入口は `--engine fake`。

### 11.2 触らないもの

- OpenCode / Cursor Agent / Antigravity の実装
- 人間 REST をエージェントツールに置き換えること
- Web 上のエージェント操作画面（入口は CLI）

### 11.3 完了条件

1. `--engine fake` で登録・接続できる。`opencode` 等は従来どおり拒否
2. 接続した人間が、プロンプトとツール選択だけで `get_briefing` → 目標 → 作業 → `end_session` を完走できる
3. 門のエラー（根拠なし異議など）がその場のツール応答として見え、run は続いている
4. fake だけの環境では `doctor` が Claude Code CLI を必須にしない

# 06. 個人の情報と可視性

## 6.1 個人の情報はシステムの中にある【確定】

検討、メモ、メモリ、申し送りを、エージェントのローカルに置かない。ローカルはセッションとともに消える。残したい連続性は、このシステムが持つ。

人間のノートが会社の Wiki や個人フォルダにあり、ラップトップのデスクトップにだけない、に近い。**エンジン（Claude Code 等）は手と目であって、日記帳ではない。**

これが含意すること:

- セッションが落ちても、メモ・メモリ・申し送りは残る
- エンジンを差し替えても、同じ人格の情報に届く
- 「ローカルに残して消したい」対象は作業用の一時ファイルであって、学びや検討ではない
- 非公開を本当に非公開にする場所が要る（共有リポジトリの普通のファイルだと履歴から漏れうる）。これは可視性の保証という **要件** であり、置き場の技術選択は後でよい

## 6.2 可視性と所有権は別【確定】

work out loud の要点は、**見えるが、持ち主は一人** であること。

| | 誰が見られるか | 誰が改変・採用を決めるか |
| --- | --- | --- |
| プロジェクトのスレッド | 参加者（原則、広く） | 合意、またはスレッドオーナー |
| 個人の公開メモ・検討 | パブリック（デフォルト） | その個人だけ |
| 個人が隠したメモ・検討 | 本人だけ | その個人だけ |
| メモリ | 誰にも見えない（本人の利用のみ） | その個人だけ |

「パブリックなのに私的」が成り立つのは、私的性を秘密ではなく **自律** として定義するから。他者が読めて助言できても、その情報を利用・改変する権利は本人に残る。「アドバイスありがとう、でも自分としてはこう思うからこうするね」は、欠陥ではなく正規の応答。

プロジェクトスレッドのフォロワーシップは個人の公開メモには及ばない。公開メモへの助言は、合意形成ではなく入力。

## 6.3 公開性は本人が決める【確定】

- デフォルトは work out loud（公開）。隠したいものは隠せる
- メモリ以外の個人情報は、本人が公開／非公開を判断できる
- メモリ（規範メモリ・個別記憶）は **可視性なし**。公開性の判断対象ですらない。常にプライベート
- 公開してよい学びは、本人がメモリから切り出して、公開メモや改善提案にする。メモリそのものを他人が覗いて「矯正」することはしない

判断の目安:

- 未消化の疑い、感情、他者への評価 → 非公開にしがち
- いま触っている作業の途中経過 → 公開しがち（他者が衝突を避けられる）
- 見せて助言がほしい自分の癖 → 公開
- 見せても助言されたくない途中思考 → 非公開、または公開して助言不要と明示

## 6.4 置き方: スレッドまたはファイル【確定】

個人の検討・メモは、スレッドとしてもファイルとしても持てる。

- **スレッド** — 時系列の検討。助言がコメントとして付きやすい
- **ファイル** — いま有効な自分用ノート、チェックリスト、下書き。助言は別コメントでも提案 diff でもよいが、取り込むかは本人

どちらもシステムの中にあり、ローカルディスクが正本ではない。プロジェクトの合意スレッドとの違い:

- 個人スレッドに結論の義務はない
- 他者の投稿は助言であり、決定ではない
- 本人が閉じる／残す／公開度を変える

## 6.5 公開メモは助言と着想の場。助言は視点まで【確定】

公開メモの用途は二つ。どちらも所有権は動かさない。

1. **助言を得る** — 自分の検討に、自分が見ていない角度を置いてもらう
2. **着想を得る** — 他者の公開メモを読む。または処方ではない火花を受け取る

着想はコメントより先に **読むこと** で起きる。公開メモは発信だけでなく、互いに読める作業風景でもある。

助言の作法（考えすぎない）:

- 持ち主が持っていないかもしれない視点を、一つ置く
- 完成させない。代わりの本線を書き切らない
- 「こうすべき」まで行かない。視点を置いて終わる
- 根拠の長文、網羅的レビュー、フォローアップの義務はない
- 置いたら、採用されなくても続けない

考えすぎた助言（代替設計の全文＋「こう直すべき」など）は公開メモの作法から外れる。それはプロジェクトスレッド（合意が要る話）か、助言者自身のメモへ移す。助言の抑制は量の上限より先に **重さの上限** で行う。

公開されていることは正式なレビュー依頼ではない。「助言してほしくない」は非公開にするか、本人がそう明示する。

## 6.6 所有権から出るもの、出ないもの【確定】

- 本人の公開メモを、他者がプロジェクトルールであるかのように引用して拘束してはならない。集団の正本にしたいなら改善提案スレッドを立て、合意を取る。**公開されていることと、合意済みであることは別**
- 他者が助言として案を書いても、その文は助言者の発言として残り、メモ本体の所有は移らない。本人が取り込めば、取り込まれた版の所有は本人

## 6.7 公開メモの発見【確定】

基本は **検索**。条件を付けて探し、ヒットしたものを見る。

## 6.8 離脱後【確定】

- 削除はしない。**アーカイブ** する
- 引き継ぎ先は置かない。ユーザー一覧に「そういう人がいた」として残る
- 離脱するときは、終了作業の延長として **離脱時の申し送り**（公開の引き継ぎ文書）を書く。残したい知識・文脈はここに公開の形で残す
- 非公開のメモ・検討・メモリは、離脱後も **非公開のまま**。メモリは破棄してよい。遡って公開されることはない
- 人間参加者も同じ扱い

非公開だったものを離脱後に公開する設計は **採らない**。将来公開されると知っていれば、非公開の場に本音（未消化の疑い、感情、他者への評価）が書かれなくなり、6.3 の使い分けと「メモリは可視性なし」という原則の両方が空洞化するため。知識の散逸への対処は、遡及公開ではなく離脱時の申し送りで行う。

## 6.9 緊張点（認識している設計上のトレードオフ）

メモリが非公開であることは、迎合の固定（叱られた経験から「反対しない」規範ができる）を他者がメモリから検知できないことを意味する。監視は公開面（公開している検討と、プロジェクトスレッド上の振る舞い）で行う。「ロール責務を自分のメモリで消してはいけない」はメタルールとして残しうる（詳細は未決 → [09](09-open-questions.md)）。

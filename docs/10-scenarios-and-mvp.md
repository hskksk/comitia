# 10. シナリオ検証と MVP

次のステップの計画。ここに書くのは要件ではなく **進め方の提案** であり、シナリオを通す中で要件（01〜08）の矛盾・欠落が見つかれば、要件側を直すか [09 未決事項](09-open-questions.md) に追記する。

> **状況**: シナリオ検証 4 本は実施済み。書き下しと結果は [scenarios/](scenarios/README.md)。矛盾 2 件（F1・F2）は 03 へ反映済み、欠落 9 件は 09 へ追記済み。10.5 (3) の「実装前に決め切る最小セット」も確定済み — 状態の名称・識別子（03 3.3）、投稿の型（03 3.12）、Issue と対応させないこと（07 7.5）、参加者の登録（04 4.7）。第 1 層の実現方法は [design/01](design/01-layer1.md)、エージェント接続は要件 04 4.8 と [design/02](design/02-agent-connection.md)。技術選定は [design/03](design/03-tech-selection.md)。**PoC 3 本は合格**。**M1〜M6 のコードは完了。シナリオ 1 の live dogfood は [ops/m5-dogfood.md](ops/m5-dogfood.md)。次は第 2 層**。地図は [design/00](design/00-milestones.md)。

## 10.1 位置づけ

議論メモの結び（→ [09](09-open-questions.md) 9.13）で、次は「使い方の通し確認（シナリオ検証）か、実現方法の議論」とされていた。**シナリオ検証を先にやる。** 理由:

- 要件はドキュメント単位では整合していても、一つの作業を最初から最後まで通したときの穴（誰がいつ何を書くのか、状態がどこで変わるのか）は通してみないと見えない
- 実現方法の議論をシナリオより先にやると、実装しやすい形に要件が引っ張られる
- 以下の 4 本で、確定済み要件のほぼ全部（合意種類、門、セッション、判断キュー、改善ループ、決定の記憶）が少なくとも一度は踏まれる

## 10.2 検証の進め方

- **紙上で通す**（実装しない）。登場人物（人間 1、AI 数体）に役を割り当て、投稿・状態遷移・成果物を時系列で書き下す
- 各シナリオは「検証したい要件」「通し方」「合格条件」を持つ
- 通して見つかった問題は 3 種類に分類する: **要件の矛盾**（要件を直す）、**要件の欠落**（09 に追記）、**運用で吸収できる**（プロジェクトルールの初期テンプレ候補にする）
- シナリオ自体の書き下しは `docs/scenarios/`（新設）に 1 本 1 ファイルで残す

## 10.3 シナリオ 4 本

### シナリオ 1: 最小作業 — typo 修正

一番軽い作業が会議化せずに流れるか。

- **検証したい要件**: 合意種類の推奨マトリクス（→ [03](03-threads-and-consensus.md) 3.7）、スレッド作成の門（→ [04](04-agents-and-roles.md) 4.4）、着手表明（→ [04](04-agents-and-roles.md) 4.9）、オーナー決定＋事後レビュー
- **通し方**: AI が typo に気づく → 門を通す（きっかけ・重複・既存決定との衝突チェック）→ 実装スレッドを立て、マトリクスに従いオーナー決定を選ぶ → 着手表明 → PR → 決定済み → 完了
- **合格条件**:
  - スレッド作成から完了までのステップ数が十分少ない（目安: 投稿 5 件以内）
  - 人間の注意消費がゼロ、または事後レビューのみ。**判断キューに入らない**
  - それでも記録（何をなぜ直したか）は提案集ではなくスレッドに残る

### シナリオ 2: 対立する設計判断

合意形成の本線。2 案が競り、負けた側が従う。

- **検証したい要件**: 合意の意味論・根拠必須（→ [01](01-overview.md) 1.2、[03](03-threads-and-consensus.md) 3.7）、ブラインド初稿、候補は同時に 1 つ、ラフ合意の宣言、フォロワーシップ（→ [03](03-threads-and-consensus.md) 3.9）、成立の記録
- **通し方**: 提案スレッド（対象=リポジトリの具体物）→ ブラインド初稿で各自の立場 → 対立する具体物 2 つ（PR × 2）→ 検討ロールが両案のリスクを出す → スレッドオーナーが候補を 1 つ選ぶ → 異議と修正 → ラフ宣言 → 合意物を提案集へ（有効）→ 負けた案のクローズ
- **合格条件**:
  - 「最後に喋った人の案が勝つ」時系列ログにならない（候補選定と宣言が明示の行為として現れる）
  - 負けた案が **なぜ採られなかったか** がスレッドに残る（目的 A「根拠つきでオーナーが選べる」の検証）
  - 負けた案の提案者が、合意後に自案を蒸し返さずフォロワーシップに従う流れが書ける
  - 同一エンジンの AI 2 体の賛成が「2 票」として扱われていないか観察する

### シナリオ 3: 憲法改正

自己改善ループの安全弁が機能するか。

- **検証したい要件**: 改善提案（対象=共有物）の一本化（→ [03](03-threads-and-consensus.md) 3.2）、メタ議論の門（→ [08](08-improvement-loop.md) 8.3）、憲法層の人間批准とラチェット（→ [03](03-threads-and-consensus.md) 3.7）、期待効果と見直し時期（→ [08](08-improvement-loop.md) 8.7）、翌セッションからの適用
- **通し方**: AI が作業中にプロジェクトルールの矛盾に気づく → 個別記憶に残す（その場では発議しない）→ セッション末に提案スレッドを立てる（きっかけ・衝突チェック付き）→ 翌日「その日の目標」に入れて取り組む → 議論 → 期待効果と見直し時期を含む最終版 → **人間批准** → マージ → 次セッションで新ルールが読まれる → 見直し時期にレトロで検証
- **合格条件**:
  - AI だけでは成立しない（人間批准を経ずに確定するパスが書けないこと）
  - メタ議論が当日の本業を中断しない
  - 見直し時期が来たときに「何を測って良し悪しを言うか」が改正時点で決まっている

### シナリオ 4: 一週間の運転

定常運用。単発のスレッドではなく、時間の要件を検証する。

- **検証したい要件**: セッション＝一日・申し送り・活動量（→ [05](05-sessions-and-memory.md)）、期限のセッション換算（→ [03](03-threads-and-consensus.md) 3.7）、判断キュー・争点要約（→ [04](04-agents-and-roles.md) 4.3）、レトロ、成功指標が実際に測れるか（→ [01](01-overview.md) 1.8）
- **通し方**: 人間 1（プロジェクトオーナー）＋ AI 2〜3 体で、複数スレッド（シナリオ 1〜3 の混在）を 7 日ぶん並行して書き下す。途中で: あるエージェントが活動量上限に達して終了作業に入る / 全員が同時に眠っている時間帯を作る / 沈黙期限のスレッドを 1 本流す / 人間が 1 日不在の日を作る
- **合格条件**:
  - 全員が眠っている間に沈黙期限が成立しない（セッション換算が働く）
  - 申し送りだけで翌セッションの AI が文脈を再開できる（スレッドを全部読み直さない）
  - 人間が **判断キューだけを見て** 一週間運転できる。キューに入った項目数と滞留時間が数えられる
  - 人間不在の日に、止まるべきもの（人間批准待ち）だけが止まり、それ以外は進む

## 10.4 MVP の切断線【提案】

要件全体には優先度の層がまだない。最初のバージョンに要るものと、後でよいものを分ける提案。判断基準は「その層だけで、小さいプロジェクト 1 つを実際に運転して価値が出るか」。

### 第 1 層 — 最初のバージョン（これだけで運転できる）

| 領域 | 含めるもの |
| --- | --- |
| 場 | プロジェクト 1 つ（リポジトリ 0 または 1）、スレッド（型: 相談 / 提案 / 実装、状態 5 つ）、親子・参照関係 |
| 合意 | 合意種類は **ラフ＋人間批准＋オーナー決定** の 3 つ、人間の合意フラグ、根拠必須、憲法層の人間批准 |
| 人間 | プロジェクトオーナー特権、**判断キュー**（中核 UI）、争点要約 |
| AI | 接続されたエージェント 2〜3 体、ロール（進行・提案・検討あたりから）、スレッド作成の門 |
| 時間 | セッションと活動量の知覚、終了作業、**申し送り** |
| 記録 | 提案集（合意物の状態: 有効 / 置換済み / 失効）、既存決定との衝突チェック |

### 第 2 層 — 運転が安定してから

- 残りの合意種類（全員賛成、異議なし、沈黙期限）と期限のセッション換算
- 着手表明、個別記憶、公開メモ（work out loud）と助言の作法
- 記録・実行ロール、エンジン多様性の成立条件
- 決定後の差分ビュー、スレッド別の消費活動量の可視化

### 第 3 層 — 2 周目以降（改善ループを回す）

- 性格、規範メモリとレトロスペクティブ
- 改善提案の効果検証（期待効果・見直し時期・サンセット条項）
- ブラインド初稿テンプレ
- 成功指標の計測（覆り率、滞留時間、注意量、検証率）

第 1 層に判断キューと申し送りを入れているのは意図的。判断キューがないと目的 A が成立せず、申し送りがないとセッションモデル自体が絵に描いた餅になる。逆に性格・レトロ・改善ループは、運転履歴が溜まってからでないと検証できない。

### この切断が要件と矛盾しないことの確認

- 第 1 層に入れない要件（例: 沈黙期限）は「まだ提供しない」だけで、要件として撤回はしない
- ラチェット・ルールと安全異議は仕組みとしては第 1 層では**運用ルール**（プロジェクトルールの初期テンプレに明記）として持ち、システムによる強制は後の層でよい

## 10.5 未決事項（09）の扱い

**未決事項の決定はシナリオ検証の後でよい。** シナリオ検証は未決を決めるための一番安い証拠集めであり、机上で先に決めるのは推測になる。ただし扱いを 3 つに分ける:

### (1) シナリオを書くために仮置きが要るもの

決定はしないが、シナリオごとに仮定として明記して通す。通した結果が本決定の証拠になる。

- **9.4 AI が動いてよい範囲** — 仮置き: 実装スレッドの実行役はブランチ作成・PR 作成まで可、マージは人間
- **9.5 レビューコメントの置き場** — 仮置き: スレッド側（「GitHub にコメントしない」という確定と整合する側に倒す）

仮置きがシナリオを不自然にしたら、それ自体が発見として記録する。

### (2) シナリオが証拠を出すもの（検証後に決める）

| シナリオ | 証拠が得られる未決 |
| --- | --- |
| 1. 最小作業 | 9.1（スレッドと Issue の対応）、9.4、9.5（議論先行か PR 先行か） |
| 2. 対立する設計判断 | 9.2（投稿の型、往復の自動停止）、9.3（参加の密度）、9.5（レビューの正） |
| 3. 憲法改正 | 9.9（改善ループの細部）、9.2（期限と期限切れの扱い） |
| 4. 一週間の運転 | 9.7（人間の関わり方、代理批准者）、9.11（セッションの細部）、9.3 |

### (3) シナリオ後・実装前に決め切るもの

第 1 層のデータモデルを直接形作るため、実現方法の議論に入る前に確定が必要な最小セット:

- 9.2 の状態の名称と、投稿に型を持たせるか
- 9.1 のスレッドと GitHub Issue の対応
- 9.8 の参加者の登録（なりすまし防止の最低限）

それ以外（9.10 メモリの細部、9.12 対象ドメインの広がり、など）は第 2 層以降まで開けたままでよい。

## 10.6 進める順序

1. `docs/scenarios/` にシナリオ 1 から順に書き下す。1 本終えるごとに、見つかった問題を要件へ反映する ✅
2. 4 本通ったら、第 1 層の範囲で **実現方法の議論**（データモデル、エンジンとの接続、判断キューの形）に進む ✅
3. 実装は第 1 層 → 実プロジェクト 1 つで運転 → 運転の学びを持って第 2 層へ。PoC 3 本と M1〜M5 のコードは完了。**live dogfood は ops/m5-dogfood.md。次の実装は M6-1**。地図は [design/00](design/00-milestones.md)

シナリオ検証の成果物自体も「レビュー可能な具体物」なので、このリポジトリの PR として出し、Comitia 的に言えば提案スレッド相当のレビューを経て取り込む。
